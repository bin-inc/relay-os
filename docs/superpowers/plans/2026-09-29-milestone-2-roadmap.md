# Milestone 2 Roadmap

**Spec:** `docs/superpowers/specs/2026-09-29-user-space-gate-design.md` (the user-space gate; milestone 2 is its first half, "Programs", version 0.3.0)

Milestone 2 moves the shell and every command out of the kernel into ring-3 programs loaded from a read-only `/bin`. It is split into seven plans (plan 3 became two while it was planned, spec §16 item 3, and so did plan 4, §16 item 5). Each one ends with software that can be tested by itself. Each plan is written just before it is executed, so it builds on the code that actually exists and on what the previous NUC check showed. All seven are written in full.

```
Plan 1 ──► Plan 2 ──► Plan 3a ──► Plan 3b ──► Plan 4a ──► Plan 4b ──► Plan 5
```

## Notes carried forward

- **CI and pull requests (all plans).** Every pull request to `main` must pass `lint`, `unit` and `e2e`. Every plan is split into PRs that are each green on their own, one branch and worktree per PR. New crates, user packages (`USER_PACKAGES` in `xtask/src/config.rs`) and scenarios are picked up by `cargo xtask ci`; a plan only touches `xtask/src/ci.rs` or the workflow when it needs a new kind of check. The unit job relies on the ubuntu-24.04 runner's `binutils` (`readelf`) and `linux-libc-dev` (Linux's error-number headers) from plan 1 on.
- **How plans are made (all plans).** As in milestone 1's plans 3–6: every task prototyped in a clone under `tmp/m2pN/proto`, one commit per task; the plan generated and replayed from it by `tmp/m2pN/gen` (adapted from plan 1's, which adds deletions and scripted steps); an independent review of the prototype whose real findings become tasks of their own, each with a test that fails first.
- **What plan 1 leaves for plan 2.**
  - `relay-rt` has `_start` (stack aligned, `rdi`/`rsi`/`rdx` passed through to `start`), `Args`, `main!`, `sys::{write, write_all, exit, Fd}`, the panic handler and the ELF note; nothing has run it yet. Plan 2's first scenario is the first time `_start` executes.
  - Programs are linked by `crates/relay-rt/user.ld` at `0x40_0000` with the target's default (`kernel`) code model, which works below 2 GiB (plan 1, decision 1). xtask's `check_program` checks every program with `readelf` at build time; the kernel's own ELF checks (spec §5.2) are plan 2's and must refuse the same things (the tests of `xtask/src/userland.rs` patch one field of `t-args` at a time; plan 2 can reuse the idea).
  - `sysimg::SysImgFs` serves `/bin` from the loader's `LOADER_DATA` pages, which the kernel never frees; `spawn` reads programs through the `MountTable` like any file.
  - `relay_abi::Call` numbers every call of spec §7.3; `relay_abi::errno` holds the numbers, but `vfs::Errno` has neither the new variants nor a mapping to numbers yet.
  - The kernel still runs the in-kernel shell over the `MountTable` that `kernel_main` builds (`session::run_shell(MountTable, bool)`); plan 2 adds the path from it to `spawn`.
- **What plan 2 leaves for plan 3.**
  - `kernel/src/proc.rs` runs one child to completion inside `wait`: `arch::user::enter` saves the waiting kernel's callee-saved registers and stack pointer, `leave` goes back to them from the child's kernel stack (`exit`, a fault), and `RUNNING` points at the running child for its system calls. The process table and the scheduler replace this; `enter`/`leave` become the context switch between saved contexts.
  - From ring 3 every call but `exit` and `write` is `ENOSYS` (`kernel/src/syscall.rs`, architecture-neutral, over the `Caller` trait). `spawn` and `wait` exist as kernel functions (`proc::spawn(vfs, path, args)`, `proc::wait(pid, out)`) with the ABI's meaning; `relay_abi::WaitStatus` has its layout, fault kinds and `Display`, but no call copies it out yet.
  - `UserSlice` (`mm/user.rs`) copies in only, through the linear map after walking the program's tables, so enabling SMEP and SMAP needs no `stac`/`clac` around copies. A program's AC and NT are cleared on `syscall` (`SFMASK`) and none of its flags reach the kernel code that waited for it (`leave` loads the kernel's flags; a debug assertion checks), but the interrupt and exception stubs still run with the program's AC: turning SMAP on needs a `clac` at the top of `irq_common` and `exception_common` (only where the CPU has SMAP; `clac` is `#UD` elsewhere) and a test in which a program sets AC and then takes a tick and a fault with SMAP on. Copying out and `UserStr` come with the calls that need them.
  - Address spaces (`mm/space.rs`) share the kernel's upper half, which `mm::init` fixes (every PML4 entry 256–511 has a table), and the kernel-stack area (`mm/kstack.rs`, PML4 entry 509) has 64 slots of a guard page and 64 KiB, one per process-table entry to come. User memory keeps 8 MiB of frames free (`mm::UserMem`).
  - Timer ticks from ring 3 enter on TSS `rsp0` and only count; the input poll on ring-3 ticks (§6.3) and `need_resched` are plan 3's. NMIs and machine checks now use the double fault's IST stack.
  - `t-fault` has every kind but `sse`, which needs CR0.TS, plus `flags-exit` and `flags-ud`; `userfault` checks each kind, a program after each, and that `free`'s memory in use is the same before and after (`expect-same`).
  - The in-kernel shell reaches programs through `shell::System::spawn`/`wait` (plan 4's `Runner` replaces them).
- **What plan 3a leaves for plan 3b.**
  - `kernel/src/syscall.rs` serves `exit`, `spawn`, `wait`, `kill`, `getpid`, `write`, `time`, `sleep` and `sys_info`'s memory kind through the `Caller` trait (`proc::Current` in the kernel, a fake in its tests); every other call is `ENOSYS` (`proc_list` and `pipe` stay so until milestone 3).
  - The fd table (`kernel/src/fd.rs`) has `File::Console` and `File::ShellOutput`; VFS files (with an offset and their open flags) and reading the console come with 3b. `read` from ring 3 is `ENOSYS`.
  - `kernel/src/tty.rs` has the console's mode and foreground group, used only for Ctrl-C; the line discipline (echo, Backspace, Enter, Ctrl-D, one line per read), end of input for processes outside the foreground group, and the `console_*` calls are 3b's.
  - Each process has its own `vfs::Cwd` (`proc::with_cwd`, `mounts::with`); `chdir` and `getcwd` from ring 3 are 3b's.
  - `relay-rt` has `sys::{write, write_all, exit, spawn, wait, kill, getpid, memory, time, sleep}` and no allocator yet.
  - The in-kernel shell keeps its transcript itself and reaches its children's output through `File::ShellOutput`; 3b brings the tee calls, which plan 4's `/bin/sh` uses instead.
  - A removal marks as gone only the current directory in the mount table at the time (spec §16 item 3): once programs `chdir` and create files (3b), a process whose working directory another one removed must not reach a freed ext2 directory, so 3b marks every process's working directory, or refuses the removal.
- **What plan 3a leaves for plan 4.** The console is polled on ticks that interrupt ring 3 and by the idle task only, as spec §6.3 says. A program that spends its ticks in the kernel (plan 4's `cat` and `cp` in ring 3) is not polled meanwhile, and a real HID keyboard with one transfer outstanding can then lose a key pressed and released between two polls (QEMU's keyboard queues, so no scenario shows it): plan 4 polls on the way back to ring 3 when a tick has passed during the call. Keyboard endpoint recovery stays in the idle task's `usb::service`.
- **What plan 3b leaves for plan 4.**
  - Every call of spec §7.3 but `proc_list` and `pipe` works from ring 3, and `relay-rt` has a wrapper for each and a heap (`alloc` works in every program). Plan 4's `SysVfs`, `SysConsole` and `SysSystem` are built over them: `SysConsole::read_byte` reads fd 0 in raw mode, `SysSystem`'s `reboot`/`poweroff` are `power` (with `POWER_FORCE` for `-f`), `uname` and `dmesg` read `sys_info`.
  - `/bin/sh` takes the console as the in-kernel shell does (spec §6.4): raw mode and its own group at the prompt (`console_mode`, `console_foreground`), line mode and the command's group while it waits; what the command did not read comes back as raw input, echoed once. It takes the console back before each read at its prompt, whatever a program left it in (spec §16 item 4).
  - Script transcripts become tees (`console_tee_push` before the script, `console_tee_pop` after; the pop's error is the failed write's, which the shell reports), so the transcript gets its programs' output and a script's script; tees are written at every `sync`, which `/bin/sh` calls after each command. This also settles milestone 1's deferred findings about a big `ctx.out` held whole and a script that redirects into its own transcript (plan 4's list below).
  - The in-kernel shell's redirection files and transcripts are nodes, not open files, so a removal does not reach them (spec §16 item 4): until plan 4, a program that removes the file the shell redirects its output into, and makes another that gets its inode, sends the rest of its output there. `/bin/sh` holds them as fds, which a removal marks gone.
- **What plan 4a leaves for plan 4b.**
  - `/bin/sh` and every command run as programs, but only by path: the in-kernel shell is still process 1, and its own commands come first. Process 1 becomes the kernel's init (spec §16 item 5): it prints `/etc/motd`, starts `/bin/sh` in `/root` (or `/`) with `Shell::greet`'s work done by the kernel, restarts it with a log line, reaches the error screen after three ends within 10 s or when it cannot start it, and collects every orphan as it ends; `/bin/sh` collects none.
  - The in-kernel shell's glue goes with the `shell` dependency: `session.rs`'s `KernelConsole`, `KernelSystem` and the shell's `run`, `File::ShellOutput` and `SHELL_OUT`, `FdTable::shell`, `renew_outputs`, `proc::wait`'s output hook, `give_console`/`take_console` (and with them plan 3b's deferred finding that they wake no leftover reader), `System::spawn`/`wait` and the in-process runner's program path (`run_program`, `Ctx::wait_program`). `KernelVfs` stays: the kernel's `spawn` reads programs through it, and `KernelVfs::shutdown` should write the tees first (plan 3b's deferred finding) if the kernel's `power` keeps using it.
  - Under the in-kernel shell a program's fd 1 is `File::ShellOutput`, which `fstat` calls a character device, so a program run by `relay-sh` cannot tell a redirection from the screen (`ls > f` lays out columns); under `/bin/sh` it can. The `utils` scenario checks only what does not depend on it; once `/bin/sh` is process 1, `fileops` and the other milestone 1 scenarios cover the rest.
  - The kernel findings carried forward: poll the console on the way back to ring 3 when a tick passed during a call (plan 3a); `console_foreground` of a group whose members are all zombies, `open(READ|CREATE)` of a directory (`EISDIR`), `POWER_FORCE` and `POWER_REBOOT` run end to end by `reboot -f` and `poweroff -f` (the e2e runner's `poweroff COMMAND` needs a variant for an unclean filesystem), a host test of `tty::push_tee`'s checks (plan 3b).
  - The console calls refusing a caller outside the foreground group are milestone 3's, with background jobs (spec §16 item 5).
- **What plan 4b leaves for plan 5.**
  - Process 1 is the kernel's init (`kernel/src/init.rs`) and the kernel has no shell (spec §16 item 6); every scenario runs under `/bin/sh`, and NUC check 4 runs `check4.sh` after check 3's scripts, with `exit` by hand. Plan 5 fixes what that NUC check shows.
  - Plan 4a's list for plan 5 stands: `flush_pages` outside `arch/`, the guest tests' unbounded loops, `read_dir`'s heap measurement.
  - A `/bin/sh` that cannot be started reaches the error screen only in a host test: no scenario builds an archive without it.
  - The tick poll's cost (spec §14): check 3's and check 4's transcripts hold `t-spin`'s counts with the poll; plan 5 measures without it (a kernel built without the poll) if those counts call for it.
  - The error screen takes the console back (raw, init's group); milestone 3's `kill`, which can end a shell while its command has the console in line mode, tests it.
- **What plan 5 leaves for milestone 3.**
  - Milestone 2 is done at 0.3.0 (spec §16 item 7): every item of spec §1.4 is met, and nothing found while planning or executing it was left undecided.
  - The console calls refusing a caller outside the foreground group come with background jobs (spec §16 items 5 and 7).
  - The error screen takes the console back (raw mode, init's group) and wakes its readers; only a shell ended while its command has the console in line mode reaches it, which milestone 3's `kill` can do, so its plan tests it.
  - Milestone 1's "still out of the gate" list below stays out, and the aarch64 port and the ABI's notes for other architectures come after the gate.
- **Deferred findings of milestone 1** (plan 6's final review, `tmp/p6/plan6-ledger-final.md`, and the ones ruled out in spec M1 §15 item 12). Each plan below decides them as milestone 1's plan 6 did: fixed with a regression test that fails first, or ruled out with its reason in the spec's §16.
  - Plan 3a (interrupts matter once the timer preempts programs and ring 3 raises exceptions), all fixed: vectors 32–47 delivered through the LAPIC get no LAPIC EOI; the interrupt-storm count never resets; a failed `timer::init` returns before masking the PIC.
  - Plan 3b (the console's line discipline is rebuilt anyway), both fixed: a lone ESC over COM1 waits for the next byte, and a keyboard Ctrl-C does not clear a half-arrived serial sequence.
  - Plan 4a (transcripts become console tees, the shell's command table splits), all settled (spec §16 item 5): a single `ctx.out` of more than 4 KiB is held whole before the transcript flush (not under `/bin/sh`, whose transcripts are tees); a script that redirects into its own transcript garbles it (ruled, as bash's would; `sh`'s documentation says so); the re-exports in `crates/shell/src/commands/mod.rs` sit inside the mod list (moved).
  - Plan 5, all fixed (spec §16 item 7): a port that keeps bouncing while connected costs up to 3 × 2 s per attach (now `UsbError::Unstable`, not tried again); `Qmp::wait_event` sets the read timeout through the writer's duplicate of the socket (now the reader's, and a message cut at the deadline is kept); the loader-rules test's comment stripping also cuts at a `//` inside a string literal; `verify-usb` shows each transcript's time but does not compare it with the script's (a transcript older than its script fails); `parse_fadt`'s offset-40 guard reads the range twice.
  - Still out of the gate (spec §15), with milestone 1's reasons: the EDID from the first handle and a `set_mode` error ending the boot; one failed ECAM window dropping the others; `check=timer` blaming the RTC; a 64-bit BAR in the last slot shown as `mem32`; the XSDT's pointers not checked against the memory map; `ls` and `rm -r` quadratic in big directories (the gate has no loops); a stick with a wrong residue; the 5 s bulk timeout; `/` not mounted again after a replug; disks over 2^32 blocks; the fakes' missing packet-level behaviour.
