# Milestone 4 · Plan 1: Lists — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `/bin/sh` runs lists. `;` separates commands, `&&` and `||` join pipelines on success or failure, `!` negates a pipeline's status and `&` starts a job in the middle of a line, all as bash 5.2 does; a command that ends after `|`, `&&` or `||` goes on to the next line, in scripts, in `X | sh` and at the prompt, which shows bash's `> `. A corpus of scripts compares the shell with the host's bash on every unit run, and the new scenario `control` runs it all in QEMU. The roadmap of milestone 4 and the spec's §15 item 1 land with this plan. It ends with `cargo xtask ci` green, `control` among the 48 scenarios.

**Architecture:** All in the shell crate; the kernel, the ABI (3) and `/bin/sh`'s `main` do not change. The parser gives a tree (`parser::List` of `Item`s, each an `AndOr` of `Pipeline`s with a `Connector` between them, a pipeline `negated` or not, an item with its background text) instead of one pipeline per line; `Shell::execute` walks it (`run_list`, `run_and_or`, `run_pipeline`) and expands each pipeline just before it runs, today's code for one pipeline unchanged below. Two flags of the shell, `cancelled` (a status of 130) and `abandoned` (a bad substitution, a line past 64 KiB), end the rest of a line. A new `reader::Reader` keeps the lines of a command until one finishes it (`ParseError::Incomplete` means "more lines"), at most 64 KiB; the interactive loop, `run_lines` (scripts) and `run_input` (`X | sh`) all read through one. `crates/shell/src/corpus.rs`, a test module, runs `crates/shell/tests/corpus/*.sh` under bash and under the in-process runner.

**Tech Stack:** Rust 1.98.1 stable, `no_std + alloc`, no new third-party crates; QEMU 8.2 under KVM with `-cpu max` (the host has the NUC's CPU model); bash 5.2.21 (interactive in a pty, `tmp/m4p1/pty_bash.py`, for the prompt; `bash FILE` for the corpus, on CI's ubuntu-24.04 too).

**Spec:** `docs/superpowers/specs/2026-10-02-programmable-shell-gate-design.md` (§1.4, §2, §4.1, §4.3–§4.5, §5.1–§5.5, §10, §11.1–§11.3, §12, §15 item 1)
**Roadmap:** `docs/superpowers/plans/2026-10-02-milestone-4-roadmap.md` — this is plan 1 of 4 of milestone 4.

## In brief

- **Size.** 18 tasks in two code pull requests, plus this plan as PR 1 (decision 1): PR 2 the tree and the lists (`;`, `&&` and `||`, `!`, `&`) with the bash corpus; PR 3 commands across lines (the `Reader`, scripts and `X | sh`, the `> ` prompt), `help` and the scenario `control`. No NUC check: nothing here is particular to the NUC, and plan 4's `check6.sh` runs lists there.
- **bash's words** (decisions 3, 4, 5), probed against an interactive bash 5.2.21 for every error: `syntax error near unexpected token` with bash's token (`;`, `;;`, `&&`, `||`, `|`, `&`, `!`), `unexpected end of file` for a command never finished. A pipeline that `&&` or `||` skips leaves `$?` alone; `!` turns 130 into 0 as bash's does; a job's text leaves `!` out, as bash's `jobs` does. Two refusals: an and-or list ending with `&` (bash runs it in a shell of its own), and any background job under the in-process runner.
- **What ends a line** (decision 2): `exit`, Ctrl-C (told by how a command ended, not by a status of 130) and an expansion that abandons the line (a bad substitution, a line past 64 KiB) in a command the shell runs itself, as interactive bash's do; in a pipeline or a background job, which bash expands in shells of their own, and for an ambiguous redirect, only that command fails.
- **Across lines** (decisions 7, 8, 9): after `|`, `&&` or `||` a command goes on past blank and comment lines; a script traces each line as it reads it; the prompt shows `> `; at most 64 KiB is kept; Ctrl-C at `> ` drops the command.
- **Three bugs the prototype found in itself**, each fixed in its task with a test that failed first: an in-process script that abandoned a line made its caller's line stop too (Task 2); Ctrl-C between two lines of a command made a script say `unexpected end of file` after the `^C`, and `! a |` did not go on to the next line (Task 12).
- **Reserved words refused until plan 2** (decision 6, Task 10): with `;` a line such as `if true; then echo b; fi` would run as commands that are not found; until the compound commands come, bash's reserved words are unsupported syntax where a command name stands.
- **The prototype's review.** A fresh reviewer read the whole prototype (then ten tasks), ran the shell's tests, throwaway probes and QEMU scenarios under KVM, and compared 54 operator soups and every interactive case with bash 5.2.21 in a pty. It found no critical, 2 important and 5 minor real defects. Each is fixed in a task of its own after the task it concerns, with a test that fails first and the mutation checks that show what it guards. It found correct: every other operator soup's token, lists with the built-ins and their state (`cd`, `wait`, `kill`, `jobs`, `exit`, `sh` scripts that end with Ctrl-C, `exit` or a bad substitution), Ctrl-C in a list with a job running, the `> ` prompt on the USB keyboard (↑, Ctrl-L, Backspace, Ctrl-C), the two flags' every use, scripts' traces and transcripts across lines, the corpus harness, the commit messages, and that no new code can panic on input. It declined to judge the reserved words, which ran as commands that are not found between this plan and plan 2: the plan now refuses them (decision 6, Task 10).

## Decisions and spec revisions introduced by this plan

The spec gets these as §15 item 1 in PR 1:

1. **The tree** (§4.1). A line parses to a `List` of items, each an `AndOr` of `Pipeline`s (`negated`, `commands`) and, ended by `&`, its background text; a blank or comment line is a list of no items. Each pipeline is expanded just before it runs, so it reads the `$?` of the one before. Plan 1 is three pull requests: its plan, the lists (`;`, `&&`, `||`, `!`, `&`, the corpus), and the reader (commands across lines, the `> ` prompt, `help`, the scenario `control`). It has no NUC check; plan 4's check 6 runs lists there.
2. **What ends the rest of a line** (§5.1, §5.2). `exit`; Ctrl-C, told by how a command ended (a program killed by it, or a command that saw it, as `wait` does), not by a status of 130, which a program may exit with, and kept as a flag so that `!` cannot hide it; and an expansion that abandons the line, a bad substitution or a line that would expand past 64 KiB, as interactive bash abandons it, but only in a command the shell runs itself (an assignment too): in a pipeline or a background job, which bash expands in shells of their own, it fails only that pipeline or job, and the line goes on. An ambiguous redirect, or variables that would hold more than 64 KiB, fail only their command, as bash's do. A script the in-process runner runs keeps an abandoned line to itself. `!` leaves the status of a command whose expansion abandoned the line as it is, bash's 1.
3. **`;`, `&&` and `||`** (§4.1). A `;`, `&&` or `||` with nothing typed before it, and bash's `case` terminators `;;`, `;&` and `;;&`, are bash's `syntax error near unexpected token` naming it; one at the end of the text needs more lines. A pipeline `&&` or `||` does not run leaves `$?` alone. An and-or list ending with `&` is `unsupported syntax: & after &&` (or `||`, the connector before the pipeline `&` would start).
4. **`!`** (§4.1, §5.1). An unquoted `!` word before anything of a pipeline's first command; each one turns the status again, as bash's does. Alone before `;`, a newline or the end it is an empty command negated, status 1; before `|`, `&&`, `||` or `&`, or before a later command of a pipeline, bash's syntax error; after a redirection, a command's name. 130 negated is 0, bash's `$?` after Ctrl-C under `!`, and the line still ends. `exit` keeps its status, and a background job's start is 0, its text without the `!`, as bash's `jobs` shows it.
5. **`&` mid-line** (§4.1). It ends an item that runs in the background and the line goes on, a job's text its own item's, on one line: a job typed across lines has its lines joined by a blank, without comments or blank lines, as bash's `jobs` shows it. The in-process runner, which has no programs, refuses a line holding a background job before any of it runs (`unsupported syntax: &`, status 2).
6. **Reserved words before plan 2** (§4.2). With `;` and `&&` a line such as `if true; then echo b; fi` would run as commands that are not found. Until plan 2, every reserved word of §4.2 and the compound commands' (`if`, `then`, `elif`, `else`, `fi`, `while`, `until`, `for`, `in`, `do`, `done`) is `unsupported syntax: <word>` where a command name would stand; plan 2 turns the compound commands' into grammar.
7. **Newlines and the reader** (§4.3, §4.5). A newline ends an item as `;` does; after `|`, `&&` or `||` the command goes on past blank and comment lines. A comment runs to the end of its line. A `\` before a newline stays `syntax error: nothing after \`, where bash joins the lines (§10). `crates/shell/src/reader.rs` keeps the lines until one finishes the command, at most 64 KiB with their newlines (`relay-sh: the command would be longer than 64 KiB`, status 2); a line that does not parse drops the command, as does one of `X | sh` over 64 KiB or not text. A command dropped before its end is dropped to its end: its later lines, up to one that would have finished it, are dropped too, so that the end of an `&&` chain never runs without its guard (a line over 64 KiB is judged by its last kilobyte or two, and dropped to be safe when that does not parse alone). While a command goes on, each line is parsed alone, and the text whole only when a line may finish it, so reading 64 KiB of lines is linear.
8. **Scripts across lines** (§5.4). Each line is traced as it is read (blank and comment lines are not) and the command runs once a line finishes it. A script ending inside a command is `syntax error: unexpected end of file`, status 2, and runs none of it; Ctrl-C between its lines ends the script with `^C` alone.
9. **The `> ` prompt** (§5.5). Each line is edited on its own and kept apart in the history, where bash keeps the command as one entry (§10). The input's end at `> ` is `unexpected end of file`, status 2, and the shell ends, as bash's does.
10. **The bash corpus** (§11.2). `crates/shell/src/corpus.rs`, a test module, runs `crates/shell/tests/corpus/*.sh` under the host's bash (`--norc --noprofile`, the environment cleared but `LC_ALL=C` and `PATH=/usr/bin:/bin`) and under the in-process runner, as `X | sh` reads its input, and compares standard output and status; bash must be 5.2 and write nothing to standard error.
11. **Left for plan 2.** The compound commands, which turn their reserved words into grammar; the 32-level bound (§4.5: lists do not nest); the Ctrl-C check between commands (a list of built-ins always ends); and the refusals of a compound command in a pipeline or with `&`.

### Task 2: `;` separates the items of a list

Spec §4.1, §5.1 and decisions 2, 3: an unquoted `;` ends an item, and the items run one after another, each synced and each reading the `$?` of the one before. `exit` and Ctrl-C (status 130) stop the rest of the line, and so does an expansion that abandons it, a bad substitution or a line that would expand past 64 KiB (`Shell::not_expanded` sets `abandoned`), in an assignment too, as interactive bash abandons the whole line; an ambiguous redirect fails only its command, and the line goes on, as bash's does. A script the in-process runner runs keeps an abandoned line to itself (`run_script` clears the flag; the prototype first leaked it, and the test that shows it came first). A `;` with nothing typed before it is bash's `syntax error near unexpected token `;'`, and `;;` (bash's `case` terminator) its error at `;;`; the parser ends a pipeline at a token through `end_pipeline`, which the later operators share. Each item's start is kept, so a background job's text is its own item's (`a; sleep 5 &`). The tests that pinned `;` as unsupported syntax become tests of this. The red run is the shell's tests: `;` is still refused, and exit, Ctrl-C and a bad substitution do not yet stop a list. Mutation checks: each of the three stops dropped, `TooLong` or `BadSubstitution` left out of what abandons, the flag never cleared at a new line or after a script, `not_expanded` skipped in an assignment, `;;` taken as `;`, the whole line taken as a job's text and a `;` with nothing before it taken, each fail a test. /// The scripts, sorted by name.
````rust
fn scripts() -> Vec<PathBuf> {
    let dir = Path::new(env!("CARGO_MANIFEST_DIR")).join("tests/corpus");
    let mut scripts: Vec<PathBuf> = std::fs::read_dir(&dir)
        .unwrap_or_else(|e| panic!("{}: {e}", dir.display()))

/// What bash 5.2 prints for `script` and its status, in the C locale with
/// no startup files.
fn bash(script: &Path) -> (i32, String) {
    let out = Command::new("bash")
        .args(["--norc", "--noprofile"])
        .arg(script)
        .env_clear()
        .env("LC_ALL", "C")
        .env("PATH", "/usr/bin:/bin")
        .output()
        .unwrap_or_else(|e| panic!("the host's bash is needed: {e}"));
    assert!(
        out.stderr.is_empty(),
        "{}: bash wrote to standard error: {}",
        script.display(),
        String::from_utf8_lossy(&out.stderr)
    );
    let stdout = String::from_utf8(out.stdout).expect("bash's output is text");
    (out.status.code().expect("bash exited"), stdout)
}

/// What the in-process runner prints for `text` and its status.
fn relay(text: &[u8]) -> (i32, String) {
    let mut h = Harness::new();
    let mut input = Bytes::new(text.to_vec());
    let status = Shell::new(&mut h.vfs, &mut h.console, &mut h.system).run_input(&mut input);
    (status, h.console.take())
}

#[test]
fn the_host_s_bash_is_5_2() {
    let out = Command::new("bash")
        .arg("--version")
        .output()
        .unwrap_or_else(|e| panic!("the host's bash is needed: {e}"));
    let version = String::from_utf8_lossy(&out.stdout);
    assert!(version.contains("version 5.2."), "{version}");
}

                "{}: bash {want:?}, relay-sh {got:?}",

        }

}
````

````rust
//! The lines a command is read from (programmable shell gate §4.3): a line
//! that leaves a command unfinished (`a &&`, `a |`) is kept until the lines
//! after it finish it. The prompt, `sh FILE` and `X | sh` all read through
//! one.

use crate::parser::{self, COMMAND_MAX, List, ParseError, Word};
use alloc::string::String;

/// What has been read of the command so far.
#[derive(Default)]
pub(crate) struct Reader {
    text: String,
}

impl Reader {
    pub fn new() -> Reader {
        Reader::default()
    }

    /// Adds a line: the command it finishes, none while the command needs
    /// more lines, or why the lines do not parse, which drops them. A
    /// command longer than [`COMMAND_MAX`] is dropped too.
    pub fn add(&mut self, line: &str) -> Result<Option<List<Word>>, ParseError> {
        if self.text.len() + line.len() + 1 > COMMAND_MAX {
            self.text.clear();
            return Err(ParseError::TooLong);
        }
        self.text.push_str(line);
        self.text.push('\n');
        match parser::parse_line(&self.text) {
            Err(ParseError::Incomplete) => Ok(None),
            done => {
                self.text.clear();
                done.map(Some)
            }
        }
    }

    /// Part of a command has been read.
    pub fn reading(&self) -> bool {
        !self.text.is_empty()
    }

    /// The input ended: a command read only in part is bash's `unexpected
    /// end of file`, and is dropped.
    pub fn end(&mut self) -> Option<ParseError> {
        let reading = self.reading();
        self.text.clear();
````

````rust
/// What was typed of a background job from `start` to `end` (its `&`), as
/// bash's `jobs` shows it: one line, its lines joined by a blank, without
/// its comments or blank lines.
fn job_text(line: &str, start: usize, end: usize, comments: &[(usize, usize)]) -> String {
    let mut typed = String::new();
    let mut from = start;
    for &(c, e) in comments.iter().filter(|&&(c, _)| c >= start && c < end) {
        typed.push_str(&line[from..c]);
        from = e;
    }
    typed.push_str(&line[from..end]);
    let lines: Vec<&str> = typed
        .split('\n')
        .map(|l| l.trim_matches([' ', '\t']))
        .filter(|l| !l.is_empty())
        .collect();
    lines.join(" ")
}
````
